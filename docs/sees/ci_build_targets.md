# CI Build Targets

## Summary

The `Build all targets` workflow (`.github/workflows/build_all_targets.yml`) only builds the boards SEES flies:

- `cubepilot_cubeorange` (default, console, bootloader)
- `cubepilot_cubeorangeplus` (default, console, bootloader)
- `cubepilot_io-v2` (IO coprocessor firmware used by both Cubes)

The metadata targets (`airframe_metadata`, `parameters_metadata`, `extract_events`) are still built.

## Why

- Upstream PX4 builds every board in CI. Some upstream boards, such as `px4_fmu-v6x_default`, are within a few hundred bytes of their flash limit. Small fork-specific changes in shared code pushed `px4_fmu-v6x_default` over the limit, which failed CI on a board we do not use.
- Restricting CI to our boards keeps the fork's firmware code and board configs identical to upstream, and makes CI fail on the flash budget of the hardware we actually fly.

## How

- The build matrix is generated by `Tools/ci/generate_board_targets_json.py`, which supports a `--filter` option (upstream code).
  ```sh
  ./Tools/ci/generate_board_targets_json.py --group --filter cubepilot_cubeorange,cubepilot_cubeorangeplus,cubepilot_io-v2
  ```
- To build an additional board in CI, add its `<manufacturer>_<board>` name to the comma-separated list in both places it appears in the workflow (the `Generate Build Matrix` step and the `Debug Matrix Output` step).
- To preview the matrix locally:
  ```sh
  ./Tools/ci/generate_board_targets_json.py --group --filter cubepilot_cubeorange,cubepilot_cubeorangeplus,cubepilot_io-v2
  ```

## Trade-offs

- We no longer check that fork changes compile on every upstream board. If a change is going to be upstreamed, upstream CI will catch this.
- The `Flash Analysis` workflow still builds `px4_fmu-v5x` and `px4_fmu-v6x` for size reporting. It is unaffected by this change.
- If CubeOrange flash becomes tight, the next step is to disable fixed-wing and VTOL modules in `boards/cubepilot/cubeorange/default.px4board`, since the fleet is multicopter-only.
